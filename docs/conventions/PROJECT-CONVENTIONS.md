# EncosyTower Project Conventions

This document is the tool-neutral authority for repository workflows and
project-level ownership rules.

## 1. Specialized Conventions

- For C# code and generated output, follow [CODING-CONVENTIONS.md](CODING-CONVENTIONS.md).
- Before staging or creating commits, follow
  [COMMIT-CONVENTIONS.md](COMMIT-CONVENTIONS.md).

## 2. Unity-Owned Files

- Root `.csproj` files and `EncosyTower.slnx` are generated by Unity and ignored
  by Git.
- Do not edit generated project files manually. Let Unity refresh their contents
  and project membership, then reload dependent tooling.
- Never run `dotnet build`, `dotnet restore`, `dotnet test`, `dotnet clean`,
  `dotnet format`, MSBuild, NuGet restore, or equivalent commands against
  Unity-generated `.csproj`, `.sln`, or `.slnx` files unless the Project Owner
  explicitly authorizes the exact command and target.
- Do not run untargeted .NET, MSBuild, or NuGet commands from the repository root
  when they could automatically select a Unity-generated project or solution.
- A general request to build, test, validate, or diagnose does not grant this
  permission. Use Unity-owned compilation and test workflows instead.
- This restriction does not prohibit commands against tracked, standalone .NET
  workspaces such as `Plugins/SourceGenerator/EncosyTower.SourceGen.slnx`, but
  task-specific validation restrictions still apply.

## 3. Samples

- `Assets/Samples` is the canonical authoring source in the development Unity
  project even though Git ignores the imported sample tree.
- `Packages/com.laicasaane.encosy-tower/Samples~` is the tracked release
  deployment output.
- Make and maintain sample changes in `Assets/Samples`, not in `Samples~`.
- Any EncosyTower package change that affects samples must also be reflected in
  the canonical `Assets/Samples` source.
- At the release gate, deploy samples with `Dev Tools > Update Version`. Its
  `DevToolsForVersion.CopyImportedSamplesToPackage` step deletes the existing
  child directories under `Samples~` before copying the canonical sample
  directories.
- Review the complete `Samples~` diff after deployment. Never hand-edit
  `Samples~` or reverse-copy independent deployment drift into `Assets/Samples`.

## 4. Source Generators

- For all Source Generator work, use
  `Plugins/SourceGenerator/EncosyTower.SourceGen.slnx`.
- Do not use the root `EncosyTower.slnx` for Source Generator work.
- Release builds refresh shipped analyzer and generator artifacts in their mapped
  Unity package destinations.
- See [Plugins/SourceGenerator/README.md](../../Plugins/SourceGenerator/README.md) for
  artifact destinations and generated-source inspection guidance.

## 5. Editor UI Asset Ownership

- Put each feature's UXML/USS in its `StyleSheets/` directory. Use a `<Feature>StyleSheetPaths` owner with
  a `ROOT` composed from the nearest shared root and explicit `UXML_PATH` / `USS_PATH` or qualified variants.
  Preserve `.meta` GUIDs when moving existing assets; update consumers and active task contracts together.
- Reuse `EncosyTower.Editor.EditorAPI.LoadAsset<T>` for required assets, `GetOrLoadAsset<T>(ref field, path)`
  for caches, and `LoadStyleSheet` / `GetOrLoadStyleSheet` for skin selection. Keep dark/light caches separate.
  Feature owners hold paths and caches; do not duplicate loading, validity or exceptions in new `*Assets` helpers.
  Direct optional asset probes remain valid when absence is an intended result.
- Cached Unity assets must reload when destroyed, not only when their managed reference is null. Required-asset
  failures retain the shared path-bearing diagnostic; do not silently render an empty Inspector.
- Search shared APIs before adding utilities or guards. Shared Editor asset guards belong to
  `EncosyTower.Editor.ThrowHelper`; type-specific invariants stay with their owner, such as
  `BuildProfileOrTarget.ThrowIfInvalid`. Do not broaden visibility or add helpers without actual reuse.

## 6. Validation Evidence

- Treat static searches, Roslyn semantic analysis, .NET builds and tests, Unity
  compilation and domain reload, Unity Test Runner results, and player builds as
  separate evidence.
- Each validation layer proves only its own result. Do not substitute one layer
  for another or claim a check that was not run.
- Follow task-specific validation restrictions. Report the exact checks and
  results, plus anything intentionally not run or left for the Project Owner.
